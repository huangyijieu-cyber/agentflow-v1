# 验证末尾长时间等待的处理

## 已确认的等待漏洞

- Runner 原先遇到异常只写日志，没有向服务端报告失败；资源获取失败也会直接退出。
- Daemon 只统计成功返回的 rollout，服务端的永久失败任务没有终态结果可供收集。
- 客户端忽略传入的 HTTP timeout，强行设置为 12000 秒；vLLM 客户端也使用 12000 秒，
  外层重试还会叠加 OpenAI SDK 的内部重试。
- Solver 的 `max_time` 在轮次边界检查，无法打断正在等待的模型请求。

这些路径都可能造成最后一条任务不再产出结果，验证端却仍等待。具体运行触发哪条路径，
需要看该次 serve_log 的异常和最后一条模型/工具请求；不能仅凭 99/100 认定是 Wiki。

## 当前机制

1. 异常以 `execution_status=failed`、错误类型和错误说明上报；不生成虚假的奖励或轨迹。
   资源获取失败也会上报，结果上报必须得到服务端确认。
2. 验证 Worker 对资源获取、求解和评分设置总执行期限；服务端独立检查领取时间，
   Worker 崩溃或无法上报时也能结束等待。服务端约每 10 秒检查一次。
3. 验证超时直接记失败，不重复调度仍可能在执行的相同样本。迟到结果不能覆盖失败状态。
4. Daemon 分别保存成功和失败结果；两者合计等于样本总数时结束。
   所有 Worker 失联、任务未领取时，由验证批次期限兜底。
5. 奖励和耗时均值仍只计算正常返回的样本。日志显示成功、失败和待完成数量；验证指标
   新增 `val/completed_count`、`val/failed_count`。计时报告新增 `failed_count`、
   `settled_count` 和 `failures`，其中包含失败 rollout ID 和错误说明。
   99 条成功、1 条失败仍是 99/100 正常完成，不会标成完整的 100 条成功验证。
6. 模型请求设置有限超时，关闭 SDK 的隐式重试。vLLM 原有外层三次尝试仍保留。
   原有网站的 429、Retry-After 等重试策略不变。

## 参数与部署

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `AGENTFLOW_LLM_REQUEST_TIMEOUT_S` | 300 秒 | vLLM/OpenAI 客户端及训练代理的单次请求超时；不等于一个 rollout 只能跑 300 秒 |
| `AGENTFLOW_VAL_TASK_TIMEOUT_S` | 1200 秒 | 单个验证任务领取后的执行期限，不包括排队时间；训练端随任务下发给 Worker |
| `AGENTFLOW_VAL_BATCH_TIMEOUT_S` | 3600 秒 | 普通验证整个批次的等待上限，包含排队时间 |
| `AGENTFLOW_PROFILE_VAL_TIMEOUT_S` | 3600 秒 | 计时验证使用的批次等待上限，保留原有变量 |

在训练端及 rollout 服务端设置相应环境变量，更新后重启两边进程。
正在运行的旧验证不会因修改文件自动加载新机制。

异步超时会取消等待，但 Python 无法强杀已经进入 `asyncio.to_thread` 的同步函数，
也不能保证取消远端已接收的推理。已发送请求由请求超时等机制收尾；服务端不再等待
这些任务的迟到结果。这次修复保障验证调度能明确结束，并不保证每个样本一定成功。
较慢的正常样本也可能触发执行期限，应结合失败明细调整预算。
